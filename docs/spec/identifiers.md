# Reliquary identifiers: content SHA-256, dedup IDs and the hash-cache contract

- **Status:** **Draft.** This spec becomes normative only when the owner accepts ADR-0006. Until then, nothing may be hashed with production secrets under it (Gate A).
- **Owner:** A1 (PLAN §2.1). Other workstreams send requirements to A1 and do not edit this file.
- **Date:** 2026-10-06
- **Decided by:** [ADR-0006](../adr/0006-content-identity-and-dedup-id.md) (Proposed)
- **Evidence:** [`docs/research/a1-content-identity.md`](../research/a1-content-identity.md)
- **Vectors:** [`identifiers-vectors.json`](identifiers-vectors.json). The generator and the three independent checkers are in `spikes/A1-S3/identifiers-v1/`.
- **Conditional parts:** which whole-file kind is active (§4) is the owner's decision DR-A1-1. The dedup scope (`scope=family` in §3) waits on DR-F3-2. Everything else is proposed as written.

The key words MUST, MUST NOT, SHOULD and MAY are used in their usual normative sense. Text marked *informative* is explanation only.

## 1. Two identities

| Identity | What it is | Key | Where it may appear | Lifetime |
|---|---|---|---|---|
| **Content SHA-256** (`sha256`) | SHA-256 of the file's exact plaintext bytes (unpadded) | none | Client hash cache; the **encrypted** metadata record; the homelab catalog; USB bundles **only inside ciphertext** | Permanent, key-independent |
| **Dedup ID** (`dedup_id`) | A keyed MAC derived from the content, tagged with a kind and an epoch (§4–§6) | the family dedup secret of one epoch | Cloud control plane, R2 object metadata or keys (subject to C1/OD-04), receipts, signed records, USB bundle manifests, logs | One epoch; re-derived at rotation (§8) |

- The plain content SHA-256 MUST NOT be sent to, or stored in, the cloud in any form other than ciphertext (ADR-0001 §2; F3 M-01).
- The homelab SHOULD address its store and catalog by content SHA-256, so that rotating the dedup secret never moves stored data. This is a requirement handed to A6, which owns the store layout (ADR-0012/0013).
- Items with no device of origin (A9 admin import) get the same `sha256` and `dedup_id` as device uploads of the same bytes. Provenance belongs in the metadata record (A2), never in an identifier.

## 2. Content SHA-256

- Algorithm: SHA-256 (FIPS 180-4) over the complete plaintext byte stream, unpadded (ADR-0007: "Dedup ID and SHA-256 are computed over unpadded bytes").
- Binary form: 32 bytes.
- Text form: 64 lowercase hexadecimal characters `[0-9a-f]`. Parsers MUST reject upper case, any other length, and surrounding whitespace. This matches the output of `sha256sum`.

## 3. Secrets and key derivation

| Name | Size | Created by | Held by | Notes |
|---|---|---|---|---|
| `S_e` | 32 bytes, CSPRNG | homelab, one per epoch `e` (D2, ADR-0008 Decision 7) | homelab (all epochs, forever); enrolled, non-revoked devices (current epoch only) | Delivery and custody: D2/D3 |
| `S_root` | 32 bytes, CSPRNG | homelab, once | homelab and every enrolled device | **Kind 04 only.** Never rotated. Absent unless DR-A1-1 picks kind 04. |
| `e` (epoch) | unsigned 16-bit, 0–65535 | homelab | everywhere an ID appears | Starts at 0 and increases by 1 at each rotation. Never reused. |

Per-kind dedup key:

```
K(e, kind) = HKDF-SHA256( ikm  = S_e,
                          salt = empty (RFC 5869: HashLen zero bytes),
                          info = ASCII "reliquary/v1/dedup-id-key/kind=" || kk || "/epoch=" || eeee || "/scope=family",
                          L    = 32 )
```

- `kk` is the kind as 2 lowercase hex digits. `eeee` is the epoch as 4 lowercase hex digits.
- `scope=family` is the only scope defined in v1. If the owner chooses per-person dedup keys (DR-F3-2 option F), a scope value per person is defined then, and the IDs are re-derived (§8).
- Implementations MUST NOT use `S_e` or `S_root` directly as a MAC key (vectors N02, N13). They MUST NOT drop the kind, epoch or scope suffix from `info` (N03, N06, N07).
- *Informative:* Proposed ADR-0008 Decision 7 writes the label as `"reliquary/v1/dedup-id-key"`. The exact bytes are the ones above. The bare label is a forbidden value (N03). Putting the epoch and kind in `info` keeps keys separate even if D2 ever derives `S_{e+1}` from `S_e`.

Kind 04 only:

```
K_root = HKDF-SHA256(ikm = S_root, salt = empty, info = ASCII "reliquary/v1/content-mac-key/scope=family", L = 32)
```

## 4. Kinds

| Kind | Meaning | Status |
|---|---|---|
| `0x00` | invalid | MUST be rejected |
| `0x01` | Whole file, **digest form** | **Proposed v1 whole-file kind** (DR-A1-1 option B) |
| `0x02` | Chunk-list ID (HMAC over the SHA-256 of a canonical chunk list, under its own HKDF label) | **Reserved**. Not designed and not valid in v1. No content-defined chunking in v1 (F3). |
| `0x03` | Whole file, **content form** (ADR-0001 wording plus HKDF epoch keys) | Alternative (DR-A1-1 option A) |
| `0x04` | Whole file, **nested form** | Alternative (DR-A1-1 option N) |
| `0x05`–`0xff` | unassigned | MUST be rejected |

**Exactly one** of `0x01`, `0x03` and `0x04` becomes the active whole-file kind when the owner answers DR-A1-1. The other two are then **retired**: never valid, never reassigned. Until the owner answers, prototypes (A0) MAY use any of them, with test secrets only. The kind byte also acts as the format version: a future construction gets a new kind value and never a reused one.

## 5. MAC per kind

Let `content` be the plaintext bytes and `d = SHA-256(content)`.

| Kind | MAC (32 bytes) | Value a client caches so it can re-derive at rotation without reading the file |
|---|---|---|
| `0x01` | `HMAC-SHA256(K(e, 0x01), 0x01 ‖ d)` | `d` |
| `0x03` | `HMAC-SHA256(K(e, 0x03), 0x03 ‖ content)` | none (re-derivation needs the bytes) |
| `0x04` | `inner = HMAC-SHA256(K_root, content)`; `mac = HMAC-SHA256(K(e, 0x04), 0x04 ‖ inner)` | `inner` (and `d` for integrity) |

- `d` and `inner` enter the MAC as 32 raw bytes, never as hex text (N05).
- The kind byte prefixes the MAC input (N01, N09).
- The full 32-byte MAC is kept. **No truncation.**

## 6. Encodings

### 6.1 Binary form (35 bytes)

```
kind (1 byte) || epoch (u16, big-endian) || mac (32 bytes)
```

This is used in CBOR or other binary records, D1 or SQLite BLOB columns, and comparisons. Equality of two IDs is byte equality of the binary form. A parser MUST reject any length other than 35 (B01, B02), kind `0x00`, the reserved kind `0x02`, and unassigned kinds (B03, B04). A little-endian epoch is a known mistake (N14).

### 6.2 Text form (64 characters)

```
"rd1-" || kk || "-" || eeee || "-" || base32(mac)
```

- `rd1` = Reliquary dedup identifier, text-format version 1. A change to the text syntax gets `rd2`. A change of construction does not; it gets a new kind.
- `kk` is the kind as 2 lowercase hex digits and `eeee` the epoch as 4 lowercase hex digits.
- `base32(mac)` is the 32-byte MAC in the RFC 4648 base32 alphabet, written in lower case (`abcdefghijklmnopqrstuvwxyz234567`), with no padding. That makes exactly 52 characters. The 4 unused low bits of the last character MUST be zero, so the last character is always `a` or `q`.
  - *Informative:* the alphabet was taken from Go's `encoding/base32` and Python's `base64`, because the RFC 4648 text is blocked from the research container.
- Worked example (test secret `S_0` = bytes 0x00…0x1f, epoch 0, empty file), vector P004:
  - `K(0, 0x01)` = `9b61754febe49311172c56382ac38cad1ffaac126ad6662abe82fecd6a0e5e1f`
  - `d` = `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
  - `mac` = `4382d542befff247a1dff5d0974505d4124e976aae674c63e01308f0ac1a361b`
  - binary = `01 0000 4382d5…361b`
  - text = `rd1-01-0000-iobnkqv677zepio76xijorif2qje5f3kvztuyy7acmepbla2gynq`

**Strict parsing.** A parser MUST accept only strings that match `^rd1-[0-9a-f]{2}-[0-9a-f]{4}-[a-z2-7]{52}$` exactly, with no surrounding whitespace or newline, and that also have a valid kind and canonical trailing bits. Everything else MUST be rejected, including:
- upper case anywhere (E01–E03);
- padding (E04, E21);
- a wrong body length (E05, E06);
- non-canonical trailing bits (E07);
- characters outside the alphabet (E08, E09);
- other text versions (E10);
- reserved or unknown kinds (E11, E12);
- a wrong epoch width (E13, E14);
- a bare 64-hex string (E15);
- a hex body (E16);
- trailing newline, dot or leading space (E17–E19);
- other separators (E20).

**Why this form** (*informative*):
- It is a single case, 64 ASCII characters from `[a-z0-9-]`, with a letter prefix. So it cannot collide on case-insensitive NTFS, FAT or exFAT. It cannot equal a Windows reserved device name or end in a dot or space. It fits R2's 1,024-byte key limit and exFAT's 255-character names (note claim K9).
- The body is base32, not hex, so a dedup ID can never be mistaken for a plain content SHA-256, which is hex. A Worker or log scrubber can reject a bare 64-hex value on sight (E15), and a bug that leaks a plain digest is visible.

### 6.3 Where each form is used

| Context | Form |
|---|---|
| Signed metadata record (`dedup_id`, `docs/spec/object-format.md`) | text |
| Worker API, JSON, logs | text |
| R2 object keys and USB file or directory names, when an ID appears in them at all (C1/OD-04 and A4 decide whether it does) | text |
| D1, SQLite, CBOR, in-memory comparison | binary |

The cloud MUST reject any ID-shaped value that is not a valid full text or binary form.

## 8. Epochs and rotation (ID side; the trigger and custody belong to D2)

1. The homelab creates `S_{e+1}` and keeps every earlier `S_e`, so old USB bundles, late uploads and in-flight records stay verifiable.
2. **Homelab re-derivation:**
   - Kind 01: from the catalog's `sha256` column.
   - Kind 04: from the catalog's `inner` column.
   - Kind 03: re-read and decrypt every stored object. If the at-rest posture is A6's A′, that means bringing the archive key online.
3. **Cloud index:** the cloud's epoch-`e` ID history SHOULD be flushed, after which devices re-seed presence under `e+1` (F3 M-14, preferred). Pushing a re-keyed index is NOT a privacy measure: old and new IDs are probably linkable through query timing, set sizes and padded-size classes. The residual linkage goes to accepted risk AR-06 (OD-17).
4. **Devices** (not revoked) receive `S_{e+1}` sealed to their enrollment key (D2/D3):
   - Kinds 01 and 04: they re-derive cached IDs from the cached `d` or `inner` with zero file reads.
   - Kind 03: they compute new-epoch IDs only for entries that are pending or not yet receipted, plus new files. Receipted entries need no new ID.
5. Retired epochs: see §7 (A3). Bundles and records carry their epoch, so the homelab can verify any epoch it holds.

*Informative:* A1-S2 measured a 1M-entry SQLite cache rotating in 3.2–6.1 s with zero source-file reads, on an x86 VM only (kind-01 mechanics; kind 04 has the same shape).

## 9. Hash-cache contract (normative for every source plugin; B5/B2/B4 supply the platform signals)

- **R1 Keying.**
  - A cache entry is keyed by (source plugin, source locator, platform file identity, size, mtime at native precision, change time or opaque version token where the platform has one).
  - It stores `sha256` (and `inner` for kind 04), bytes hashed, time hashed and status.
  - Dedup IDs are derived per epoch and are never the primary cached value.
  - ADR-0001 §3's tuple is the minimum. Unix adds ctime and inode. Windows `FILE_BASIC_INFO.ChangeTime` is used only if B5 shows it is reliable and cannot be set from user mode (it is a settable field of `SetFileInformationByHandle`). iOS uses the PhotoKit version token. Android signals come from B2.
- **R2 Fail-safe.** Any recorded signal that differs, or that the plugin can no longer supply, means rehash.
- **R3 Racy window.**
  - At the start of a scan, the client writes a marker on the same volume and uses the marker's filesystem-reported mtime as `T_ref` (git compares against the index file's own mtime).
  - An entry whose file mtime is ≥ `T_ref − G` is *racily clean* and MUST NOT be trusted on the next scan. `G` = max(the volume's timestamp granularity, 2 s); FAT write time has 2 s resolution.
  - Where no marker can be written (read-only media, MediaStore), the plugin MUST treat entries modified within `G` of the scan start, as the volume reports it, as racy, or define a stricter bound (B5/B2).
  - **FAT/exFAT local time:** FAT stores local time, and reported mtimes can shift by whole hours across DST or time-zone changes. Such a shift MUST be treated as a change (rehash). It MUST NOT be skipped as "same file". B5 MAY schedule these rehashes cheaply.
  - **Quiescence:** pass 1 MUST NOT start on a file modified within `Q ≥ 2G` (B5 sets `Q`).
- **R4 TOCTOU.**
  - Take stat snapshots before and after pass 1 and around every encryption window. On any change, mark the entry "unstable" and requeue it.
  - Re-hashing during encryption is optional. R5 is the end-to-end guarantee.
- **R5 End-to-end.** Values from pass 1 are never proof. The homelab check in §7 row 1 is.
- **R6 Sampled re-verification.** Re-hash a random sample of cache hits over time. A mismatch raises an alert. B5 sets the rate against BUD-SCAN and BUD-BAT-D.
- **R7 Open check.** After opening a file, re-check that it is still a regular file (restic `fstat` after open).
- **R8 Cache provenance.** The cache records its own device and install ID. A cache that was copied or restored (for example from an OS backup) MUST be treated as entirely racy.

## 10. Conformance

An implementation conforms when it reproduces every value in `identifiers-vectors.json` and rejects every negative. For positives, "every value" means `sha256`, `key`, `inner`, `mac`, `id_binary` and `id_text`, computed with **streaming** input in irregular feed sizes. It must also pass the C2SP Wycheproof `hmac_sha256_test.json` and `hkdf_sha256_test.json` sets. This applies to:
- the shared Rust core;
- the homelab importer, which MUST run the same suite, so the A9 equality holds by test and not by assumption;
- any second-language implementation (Kotlin, Swift, TypeScript).

The vectors cover:
- the empty file;
- SHA-256 padding and block boundaries (55, 56, 63, 64, 65);
- 1023–1025, 65535–65537 and 1 MiB;
- 2³² − 1, 2³² and 2³² + 1 bytes;
- epochs 0, 1, 0x0102 and 0xffff;
- 14 domain-separation negatives and 25 encoding negatives.

Measured agreement on 2026-10-06 (Rust, Python and Node, plus `sha256sum` and `openssl` spot checks) is in `spikes/A1-S3/identifiers-v1/README.md`.

When DR-A1-1 is decided, the retired kinds' positives are moved to a `retired` section and kept as negatives (they MUST NOT be accepted).
