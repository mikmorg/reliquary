# Reliquary object format

- **Status:** Draft (Wave 1). Not normative until ADR-0007 is Accepted. Sections marked **Provisional** may change in Wave 2.
- **Owner:** A2 (ADR-0007). Other workstreams supply requirements; they do not edit this file.
- **Date:** 2026-10-06
- **Evidence:** `docs/research/a2-object-envelope.md`; `docs/research/content-encryption-format.md` (CE, T1 spike 2); spikes `spikes/A2-S2/` (code), `spikes/A2-S3/` (vectors), `spikes/A2-S4/` (rejection cases).
- **Key words:** MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119 (RFC not re-read in this run; datatracker was blocked).

## 1. Scope

This spec defines:
- the **content object** (one per uploaded file version);
- the **Reliquary profile** that ingest enforces on top of age v1;
- the encoder rules for resumable, hedged encryption;
- the **metadata record** envelope (provisional);
- the **ingest verification order** and error codes;
- the read and restore rules, padding, versioning and conformance vectors.

It does not define the dedup-ID construction (`docs/spec/identifiers.md`, A1), receipts and the ingest state machine (`docs/spec/ingest-protocol.md`, A3), bundles and manifests (`docs/spec/bundle-format.md`, A4), or the R2 key layout (C1).

## 2. Terms

| Term | Meaning |
|---|---|
| age v1 | The file format in the C2SP age spec (`C2SP/C2SP @ main : age.md`). |
| X-Wing stanza | An age stanza of type `mlkem768x25519` (HPKE SealBase, KEM MLKEM768-X25519, HKDF-SHA256, ChaCha20Poly1305, info `age-encryption.org/mlkem768x25519`). |
| I_e | The homelab **ingest** key for epoch e (an `mlkem768x25519` identity). Devices encrypt to it. |
| X, R | The homelab **archive** key and the offline **recovery** key (ADR-0008). Only the homelab writes stanzas to them. |
| h0 | The exact header bytes a device wrote: from `age-encryption.org/v1\n` up to and including the `--- <mac>\n` line. |
| prefix_len | len(h0) + 16 (the payload nonce). |
| Trust bundle | The owner-signed document that tells a device its epoch, recipients and profile (D3/D5; CE §10). |

## 3. Layering

A Reliquary reader has three separate layers. Implementations MUST keep them separate.

1. **age v1 decoder.** Parses and decrypts any valid age v1 file. It MUST pass every applicable CCTV vector (§10.1), including the low-order rejection.
2. **Reliquary profile validator.** Runs on the parsed header **before** decryption and before any catalog write. It rejects valid age files that are outside the profile (§5).
3. **Record and binding verifier.** Checks the signed metadata record and binds it to the object (§7, §8).

Some CCTV vectors expect a decoder to **succeed** on files the profile rejects. A decoder that rejects them fails CCTV; a profile that accepts them fails this spec. §10.1 lists them.

## 4. Content object v1

### 4.1 Format

A content object is a standard binary age v1 file. Byte layout follows the C2SP age spec and CE §5, with these values:

| Name | Value |
|---|---|
| CHUNK_PT | 65,536 bytes |
| TAG | 16 bytes |
| CHUNK_CT | 65,552 bytes |
| Header, one X-Wing stanza | 1,627 bytes (measured with four encoders) |
| Header, two X-Wing stanzas | 3,184 bytes |
| prefix_len | header + 16 (1,643 or 3,200 bytes). A **layout field**, never a constant |
| n_chunks | max(1, ceil(pt_len / 65,536)) |
| ct_len | prefix_len + pt_len + 16 · n_chunks |

- The payload is age STREAM: payload_key = HKDF-SHA-256(ikm = file key, salt = nonce, info = `payload`); chunk *c* is ChaCha20-Poly1305(payload_key, nonce12(c), pt_c) with the last-chunk flag. Every chunk except the last holds exactly 64 KiB; the last chunk is empty only when the plaintext is empty.
- No armor.
- **Valid lengths** (CE §5.4). With body = ct_len − prefix_len, full = body div 65,552 and rem = body mod 65,552, a reader MUST reject: body < 16; rem in 1..15; rem = 16 with full > 0.

### 4.2 Plaintext

- The plaintext is the file's bytes, optionally followed by zero padding (§9). No compression in v1 (`content_encoding` = `identity`).
- `sha256` and `dedup_id` are computed over the **unpadded** bytes.

## 5. Reliquary profile v1

A device-written object MUST satisfy all of these. Ingest MUST reject any object that does not (E_PROFILE), even if it is valid age.

1. Every stanza has type `mlkem768x25519`. No `X25519`, `scrypt`, `p256tag`, `mlkem768p256tag`, plugin or unknown ("grease") stanzas.
2. The stanza count equals **exactly** the count the device's trust-bundle epoch prescribes. Under ADR-0007 Decision 3 that is **1**.
3. The single stanza MUST open with that epoch's I_e (current or escrowed). A stanza that does not open is E_OBJECT_NO_MATCH.
4. The X-Wing ciphertext's X25519 share MUST NOT give an all-zero X25519 shared secret (low-order point). Reject with E_OBJECT_HEADER. Implementations MUST do this in project code, not rely on a crate default.
5. Encoders MUST NOT mix PQ and non-PQ recipients (age SHOULD NOT; enforced here as MUST).

Homelab-written stored headers use profile `stored-v1`: exactly {X, R}, both PQ (`mlkem768x25519`, or `mlkem768p256tag` for R if ADR-0008 picks a hardware R). A `{mlkem768x25519, mlkem768p256tag}` header measured 3,236 bytes with Go age 1.3.2.

### 5.1 Parser limits (provisional; confirm in Wave 2 with G2 fuzzing)

| Limit | Value | Error |
|---|---|---|
| Header length | ≤ 16,384 bytes | E_OBJECT_HEADER |
| Stanzas parsed | ≤ 16 (then the profile count applies) | E_OBJECT_HEADER / E_PROFILE |
| Encrypted record batch | ≤ 1 MiB | E_RECORD_TOO_LARGE |
| base64 | standard alphabet, unpadded, canonical (as age requires) | E_OBJECT_HEADER |

Parsing MUST be in memory-safe code, before any expensive work (D1 SR-22).

## 6. Encoder rules (device)

### 6.1 Hedged derivation

A 32-byte CSPRNG seed is expanded with HKDF-SHA-256, salt = SHA-256(plaintext). All per-object secrets come from this one derivation:

| Output | HKDF info | Length |
|---|---|---|
| file key | `reliquary/v1/hedge/file-key` | 16 B |
| payload nonce | `reliquary/v1/hedge/payload-nonce` | 16 B |
| X-Wing encapsulation randomness for stanza *i* | `reliquary/v1/hedge/xwing-encap/<i>` | 64 B |

- An encoder MUST NOT combine an independently drawn file key with stored or derived encapsulation randomness, or the reverse. (The same encapsulation randomness with a different file key would reuse the stanza's AEAD key and nonce.)
- The encapsulation randomness is supplied to the KEM through a seeded RNG that MUST assert it was asked for exactly 64 bytes per stanza. With `hpke` 0.14.1 the deterministic entry point is crate-private, so this is the only route.
- The seed is never stored. The header is built once and kept in the sealed upload state.

### 6.2 Resumable encryption

The encoder follows CE §7 (multipart layout) and §8 (journaled resume, release rule, stat checks) with prefix_len from §4.1. In particular:
- no byte of chunk *c* reaches the network or a shared file until its tag equals the journaled tag or the tag has been durably journaled (CE §8.3);
- a source change detected by stat checks aborts and re-queues the upload;
- after commit, the per-upload key material is deleted.

### 6.3 Device-side state

- The sealed state and journal MUST be excluded from OS backups (Android `noBackupFilesDir` and `allowBackup=false`; Time Machine and VSS exclusions), and SHOULD be sealed by a non-exportable keystore key (B6, B2, D3).
- Encoders SHOULD refuse to produce any header outside the profile (negative test in CI).

### 6.4 Dependencies

Rust implementations MUST pin `hpke`, `x-wing` and `ml-kem` with `=`. The tested set is `hpke` 0.14.1, `x-wing` 0.1.1, `ml-kem` 0.3.2. Any bump MUST pass §10 first. The KEM is defined by the C2SP age spec and the vectors in §10, not by a crate's draft label.

## 7. Metadata record (Provisional)

### 7.1 Envelope

- Each record is a C2SP **signed-note**: the text is one line of I-JSON (compact, UTF-8, no duplicate keys), then a blank line, then one signature line per signer.
- The signer is the device. The key name and type are the ones registered for that device in the trust bundle (D3 decides the type; Ed25519 `0x01` and ECDSA P-256 `0x02` are candidates). A hybrid or PQ type is reserved through signed-note type `0xff`.
- Records travel in **record batches**: one age file (profile §5) whose plaintext is a sequence of length-prefixed signed notes. Each note is a separate per-(device, file) signed unit. Batch framing is A4's to fix (ADR-0011).
- `record_sha256` = SHA-256 of the exact signed-note bytes of one record. Receipts bind it (A3).

### 7.2 Fields (sighting kind, v0)

Base list: `docs/design/data-model.md` §6.1, with these changes and additions.

| Field | Type | Notes |
|---|---|---|
| `v` | integer | Record version; 1 |
| `kind` | string | `sighting`, `tombstone`, `scan_checkpoint`, `source`, `device_info` (H4) |
| `record_id` | string, random 128-bit | Idempotency key; same across USB→R2 fallback |
| `device_id`, `device_seq` | string, integer | `device_id` MUST equal the signing key's admitted device |
| `recorded_at` | RFC 3339 time | Device time; context only |
| `dedup_id` | A1 text form, with epoch | |
| `sha256` | hex | Unpadded plaintext |
| `size` | integer | True, unpadded size |
| `padded_len` | integer or absent | Present when padding is on (§9) |
| `content_encoding` | string | `identity` in v1 |
| `object` | object or `null` | `null` marks a dedup hit |
| `object.h0_sha256` | hex | SHA-256 of h0 |
| `object.header_mac` | base64 | The MAC from the `---` line |
| `object.ct_len`, `object.prefix_len` | integers | |
| `object.profile`, `object.stanzas` | string, integer | e.g. `pq-v1`, 1 |
| source fields | | `source_id`, `source_locator` (raw and display; `*_raw_b64` for non-UTF-8 paths), `path`, `name`, `mtime_ns`, `ctime_ns`, `btime_ns`, `file_id`, `first_seen_at`, `source_version`, `source_hints` (namespaced) |
| `chunk_list` | reserved | A1 |

- The R2 staging key and USB paths MUST NOT appear in the signed record. They map to `h0_sha256` outside the signature.
- **Evolution:** unknown fields are preserved and ignored; no field changes meaning within a `v`; `kind` is open.

## 8. Ingest verification (homelab)

The homelab MUST complete every step below before writing anything to the catalog or the store. On any failure it stores nothing and returns the error code.

**Records:**
1. Decrypt the record batch (§5 profile applies). Size limit §5.1.
2. Parse each signed note strictly (E_RECORD_FORMAT, E_RECORD_FIELDS, E_RECORD_KIND).
3. Verify the signature against a device key the homelab **admitted through a path the cloud cannot forge** (D1 SR-14; mechanism in ADR-0014): E_SIG_UNKNOWN_KEY, E_SIG_KEY_HASH, E_SIG_INVALID. `device_id` MUST match the key (E_DEVICE_MISMATCH).
4. Replay checks: a committed `record_id` with different content (E_REPLAY_RECORD_ID); a `device_seq` already used by another record (E_REPLAY_SEQ). An exact replay of a committed record is idempotent: re-issue the receipt, add no row. A3 defines how E_REPLAY_SEQ surfaces as a health issue.

**Object** (when `object` is not `null`):
5. **Exact header match.** SHA-256 of the received header bytes MUST equal `object.h0_sha256` (E_BINDING_HEADER). This is a security check: it is the only check that detects a party who knows the file key and has rewrapped the header. A mismatch MUST also raise an alarm. It happens before any homelab rewrap.
6. Profile and low-order checks (§5): E_PROFILE, E_OBJECT_HEADER.
7. Unwrap the file key (E_OBJECT_NO_MATCH) and verify the header MAC (E_OBJECT_HMAC).
8. Length binding: object length = `ct_len`, header length + 16 = `prefix_len`, and the length implies `padded_len` (or `size`) per §4.1 (E_BINDING_LENGTH, E_BINDING_PREFIX, E_BINDING_SIZE, E_LENGTH_INVALID).
9. Decrypt the whole object to a temporary file, verifying every chunk and the final chunk (E_STREAM_AUTH, E_STREAM_TRUNCATED, E_STREAM_TRAILING).
10. SHA-256, dedup ID and size of the unpadded plaintext MUST match the record (E_CONTENT_MISMATCH).

**Dedup hit** (`object` is `null`): the committed content for `dedup_id` MUST match `sha256` and `size` (E_DEDUP_MISMATCH); otherwise the record waits (pending, no receipt).

**After success:** commit atomically, then sign the receipt. The homelab's signed receipt is the durable authority. Catalog rebuilds, fixity checks and provenance MUST NOT re-verify device signatures as authority.

**Panics:** a panic in a decoder or crypto library is a reject. Server code MUST NOT call HPKE auth-mode paths (`hpke` 0.14.1 panics on X-Wing auth).

### 8.1 Error codes

| Code | Meaning |
|---|---|
| E_RECORD_DECRYPT | Record batch does not decrypt |
| E_RECORD_TOO_LARGE | Record batch over the limit |
| E_RECORD_FORMAT, E_RECORD_FIELDS, E_RECORD_KIND | Record does not parse, has bad fields, or an unknown kind for its `v` |
| E_SIG_UNKNOWN_KEY, E_SIG_KEY_HASH, E_SIG_INVALID | Unknown or unadmitted key; key hash mismatch; bad signature |
| E_DEVICE_MISMATCH | `device_id` does not match the signing key |
| E_REPLAY_RECORD_ID, E_REPLAY_SEQ | Replay or sequence reuse |
| E_BINDING_HEADER | Header bytes differ from `h0_sha256` (new; replaces the spike's E_BINDING_HEADER_MAC) |
| E_PROFILE | Valid age, outside the profile |
| E_OBJECT_HEADER | Header does not parse, exceeds limits, or has a low-order share |
| E_OBJECT_NO_MATCH | No stanza opens with the expected key |
| E_OBJECT_HMAC | Header MAC does not verify |
| E_BINDING_LENGTH, E_BINDING_PREFIX, E_BINDING_SIZE, E_LENGTH_INVALID | Length fields disagree or the length is invalid |
| E_STREAM_AUTH, E_STREAM_TRUNCATED, E_STREAM_TRAILING | Chunk authentication fails; final chunk missing; data after the final chunk |
| E_CONTENT_MISMATCH | Plaintext SHA-256, dedup ID or size differs from the record |
| E_DEDUP_MISMATCH | Dedup-hit record does not match committed content |

All codes except E_BINDING_HEADER were exercised in A2-S4 on the earlier record layout.

## 9. Padding (Provisional; ADR-0007 Decision 6)

- When enabled, the plaintext is the file followed by zero bytes up to padded_len = Padmé(size) (F3 C8; reference `dedis/purb padding.go`).
- Per-file overhead bounds: ≤ 3.125 % for 64 KiB–4 GiB, ≤ 6.25 % for 256 B–64 KiB, ≤ 1.5625 % at ≥ 4 GiB.
- Every size visible to the cloud (presence checks, URL issuance, multipart layout, Content-Length, receipts) MUST be the padded size.
- Readers MUST truncate the output to `size` from the record. Stock `age -d` returns the padded bytes.

## 10. Conformance

### 10.1 CCTV

Every decoder MUST pass the applicable vectors of `c2sp.org/CCTV/age` (2026-09-25 set, 50a8ecf2a220). Armored and scrypt-only vectors are not applicable to the profile. The **profile validator** is then expected to reject these decoder-success vectors:

| CCTV vector | Decoder expects | Profile result |
|---|---|---|
| `hybrid_and_x25519` | success | E_PROFILE (mixed) |
| `hybrid_grease` | success | E_PROFILE (unknown stanza) |
| `hybrid_multiple_recipients` | success | E_PROFILE (count ≠ 1) |
| any X25519-only vector | success | E_PROFILE |

`hybrid_low_order` and `hybrid_identity` expect a header failure and MUST fail in the decoder. (A decoder built on plain `hpke` 0.14.1 accepts them; A2-S3.)

### 10.2 Project vectors

`spikes/A2-S3/vectors/` holds 15 vectors in CCTV format. They are **encrypt-direction** vectors: each is regenerated byte for byte from the seed and context in its comments. They move to `docs/spec/vectors/` when this spec is accepted.

| Vector | Decoder expects | Profile result |
|---|---|---|
| `rq_pq1_empty`, `rq_pq1_1byte`, `rq_pq1_64k_exact`, `rq_pq1_64k_plus1`, `rq_pq1_3chunks` | success | accept |
| `rq_pq2_second_identity` | success | E_PROFILE under a 1-stanza epoch (accept under `stored-v1`) |
| `rq_pq1_grease`, `rq_pq1_mixed_x25519`, `rq_x25519_legacy` | success | E_PROFILE |
| `rq_pq1_low_order`, `rq_pq1_header_truncated` | header failure | — |
| `rq_pq1_no_match` | no match | — |
| `rq_pq1_bad_mac` | HMAC failure | — |
| `rq_pq1_drop_final_chunk`, `rq_pq1_trailing_data` | payload failure | — |

(The expected results are in each vector's `expect:` line; this table summarizes them and the vector files win on disagreement.)

### 10.3 Required CI

- CCTV and project vectors against every decoder (Rust client, any Rust homelab tool, Go age as the oracle) on every dependency bump (G2).
- A negative test that no encoder path writes a mixed, extra or non-profile stanza.
- Parser fuzzing against §5.1.
- A snapshot-rollback-and-edit test for §6.1 (G2; not yet written).

## 11. Read and restore rules

- Random access follows CE §5.5: read the prefix, unwrap and verify the MAC, check the length (§4.1), **authenticate the final chunk**, and only then serve chunk *i*.
- A restore or admin tool MUST write to a temporary file and expose output only after the final chunk and the record's SHA-256 verify. age releases authenticated non-final chunks before truncation is detected.

## 12. Versioning and agility

- **Recipients:** a new recipient type or set needs only a header rewrite by the homelab. A rewrap is **not** revocation: the file key does not change.
- **Stored-header rewrite:** write a new object, verify it (open with X; R checked by the sampled drill), fsync, then swap atomically. Never rewrite in place.
- **Payload suite:** fixed by age v1. A new suite means re-encrypting under a new profile.
- **Records:** integer `v`; signature types through the trust bundle; a hybrid or PQ device signature type is reserved and is to be reviewed before 2030 (ADR-0007 Decision 5).
