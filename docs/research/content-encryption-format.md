# Content encryption format and resumable uploads (spike result)

- **Date:** 2026-09-29
- **Status:** Spike complete. The recommendation is ready for the owner's decisions (§16).
- **Spike code (throwaway):** [`spikes/content-encryption/`](../../spikes/content-encryption/). Results: 161/161 checks pass (`evidence/test_output.txt`).
- **Answers:** ADR-0001 open question "Resumable uploads vs. encryption randomness", and `client-stack.md` spikes 2 and 7 (spike 7 only on x86).
- **Method:**
  1. Read the `age` crate 0.11.5/0.12.1 and RustCrypto sources from static.crates.io, and the C2SP age spec.
  2. Built a Rust prototype.
  3. Checked every object with the **Go `age` 1.1.1 CLI** and the **Rust `age` crate**. Signatures are checked with Go `crypto/ed25519`, and dedup IDs against a Python HMAC/HKDF reference.
  4. Two adversarial reviews (crypto, engineering) followed. All their critical and major findings are addressed in §12.
- **Not exercised:**
  - Real R2 (no account; developers.cloudflare.com is blocked).
  - Real phones (no ARM hardware).

## 1. Summary

1. **Every content object is a standard age v1 file** with one X25519 stanza for the homelab key, so `age -d` decrypts it. Our own encoder (about 150 lines on RustCrypto) writes it, because the `age` crate cannot resume.
2. **Resume without storing ciphertext.** The device persists a few things per upload:
   - the 184-byte prefix and a 32-byte payload key, sealed under a per-upload keystore key;
   - an append-only journal holding each chunk's 16-byte Poly1305 tag and each part's ETag.

   Any missing part is regenerated byte-identical from the source file.
3. **Keystream-reuse guard.** No byte of chunk *c* leaves the device until one of two things holds:
   - the chunk's tag equals the tag already journaled (same plaintext);
   - the new tag has been fsynced to the journal.

   Stat snapshots (size, mtime, ctime, file ID) abort the upload if the source changes. The guard works at chunk granularity, so parts can also be streamed with bounded memory.
4. **Parts:**
   - P = k × 65,552 B, with k = 80·2^j. The default P is 5,244,160 B (about 5.0 MiB), which allows objects up to 52.4 GB. Doubling k raises the limit, up to 26.8 TB at the largest P (2.5 GiB).
   - Objects of one part go up in a single PUT with no resume state.
   - Staged objects are keyed per upload and never overwritten.
5. **Metadata** is a separate small age file. Inside the encryption, the device signs it with its Ed25519 enrollment key.
6. **A file is "protected" only when the device holds a homelab-signed commit receipt.** It verifies the receipt against a trust bundle pinned at enrollment (QR/USB kit). The homelab commits and signs only after it has decrypted and verified the whole object.

## 2. Problem and requirements

- Devices encrypt each file on the device to the homelab X25519 key, then upload it to R2 with presigned multipart uploads:
  - parts are 5 MiB–5 GiB;
  - at most 10,000 parts;
  - every part except the last must be the same size.
- Phones are interrupted constantly, so a resumed upload must continue where it stopped.
- age picks a random file key and ephemeral key on each encryption. Re-encrypting after an interruption therefore changes every byte, and the parts already uploaded become invalid.
- Storing the whole ciphertext before upload doubles storage use on phones.

| Requirement | How the design meets it |
|---|---|
| Streaming, constant memory | Buffered mode holds 1 part (9.9 MB peak RSS). Streaming mode holds W chunks (4.9 MB at W = 16) |
| Every chunk authenticated; truncation and reordering detected | age STREAM: per-chunk AEAD, a counter nonce and a last-chunk flag (59 tamper cases) |
| Random access for restores | 64 KiB chunks at fixed offsets (§5.5) |
| Dedup ID and SHA-256 over the whole plaintext, in one pass | Pass 1 reads once and computes SHA-256 and HMAC (§6) |
| Decryptable by an independent implementation | Standard age v1. Go `age` 1.1.1 and the `age` crate decrypt every test object |
| Encrypted per-file metadata | Signed record in a separate age file (§9) |
| Only the homelab can decrypt | Devices hold only the recipient public key. The one exception is the in-flight upload's own payload key (§12, R-2) |

## 3. Alternatives considered

| Option | Verdict | Why |
|---|---|---|
| Store the full ciphertext, then upload | Rejected | Doubles storage on phones |
| Supply the file key to the `age` crate | Not possible | `new_file_key()`, `Nonce::random()`, `PayloadKey` and `Stream::encrypt` are `pub(crate)`. `StreamWriter` always starts at chunk 0 and cannot seek. The X25519 recipient draws its own ephemeral key. The crate is still used on the decrypt side, where it can seek |
| Deterministic keys from long-term secrets, e.g. file key = HMAC(secret, SHA-256) | Rejected | Breaks age's CSPRNG requirement. A device secret would become a standing ability to decrypt or confirm any file whose hash is known, which breaks "devices never decrypt" |
| One age file per part | Rejected | The object is no longer one age file. Dropped or reordered parts go undetected without a signed manifest. Each part carries about 200 B of header, and padding is needed to keep parts the same size |
| Custom chunked format, with age only wrapping the key | Rejected | Needs our own spec and decryptor, and loses verification with stock age tools. The only gain is less tag overhead, which is already 0.024% |
| Pad the header so parts align to chunks | Rejected | Wastes about 64 KiB per file. The constant boundary offset is easy to handle |
| Per-part plaintext SHA-256 digests from pass 1 (first prototype) | Replaced | Cost 2 extra SHA-256 passes per byte. It protected only whole buffered parts, not streamed ones. Replaced by chunk tags recorded lazily (§8.3) |

## 4. Where this sits

```
device: pass 1 (hash) → Worker "missing?" + claim → generate/upload parts → Complete → PUT metadata → wait for receipt
homelab: pull object + metadata → verify everything → commit → sign receipt → Worker relays receipt to device(s)
```

## 5. Content object v1 (byte-level)

### 5.1 Constants

| Name | Value |
|---|---|
| CHUNK_PT (plaintext per chunk) | 65,536 |
| TAG | 16 |
| CHUNK_CT | 65,552 |
| HEADER_LEN (one X25519 stanza) | 168 |
| NONCE_LEN | 16 |
| prefix_len | 184. It is a **layout field**, not a constant (§12, R-7) |
| n_chunks | max(1, ceil(pt_len / 65,536)) |
| ct_len | prefix_len + pt_len + 16·n_chunks. Overhead is 0.024% + 200 B |

### 5.2 Header: exactly 168 ASCII bytes

```
age-encryption.org/v1\n                       22 B
-> X25519 <b64 epk, 43 chars>\n               54 B
<b64 wrapped file key, 43 chars>\n            44 B
--- <b64 header MAC, 43 chars>\n              48 B
```

- base64 is standard alphabet, unpadded and canonical. The stanza has no recipient identifier, so objects are anonymous.
- **Hedged randomness.** A 32-byte CSPRNG seed is expanded with HKDF-SHA256, using salt = SHA-256(plaintext):

  | Output | HKDF info | Length |
  |---|---|---|
  | file_key | `reliquary/v1/hedge/file-key` | 16 B |
  | esk | `reliquary/v1/hedge/x25519-ephemeral` | 32 B |
  | payload nonce | `reliquary/v1/hedge/payload-nonce` | 16 B |

  - With a working RNG the outputs are indistinguishable from fresh CSPRNG draws, so age's requirement holds.
  - If the RNG repeats (VM snapshot or clone), different plaintexts still get different keys.
  - The seed is never stored.
- The key wrap:
  - epk = X25519(esk, basepoint).
  - shared = X25519(esk, homelab_pk). Abort if shared is all zeros.
  - wrap_key = HKDF-SHA256(ikm = shared, salt = epk ‖ homelab_pk, info = `age-encryption.org/v1/X25519`).
  - Stanza body = ChaCha20-Poly1305(wrap_key, nonce = 0¹², file_key), 32 B.
- MAC = HMAC-SHA256(HKDF(ikm = file_key, salt = empty, info = `header`), header bytes up to and including `---`).

### 5.3 Payload

- Bytes [168, 184) hold the payload nonce.
- payload_key = HKDF-SHA256(ikm = file_key, salt = nonce, info = `payload`). The file key is then zeroized.
- Chunk *c* sits at offset prefix_len + c·65,552 and holds ChaCha20-Poly1305(payload_key, nonce12(c), pt_c) ‖ tag.
- nonce12(c) = 11-byte big-endian *c* ‖ (0x01 if *c* is the last chunk, else 0x00).
- Every chunk except the last holds exactly 64 KiB of plaintext. The last chunk is empty only when the whole file is empty.

### 5.4 Valid object lengths

body = ct_len − prefix_len, full = body div 65,552 and rem = body mod 65,552. **Reject** when:

- body < 16;
- rem is in 1..15;
- rem = 16 and full > 0 (an empty final chunk after a full one).

Otherwise n = full (if rem = 0) or full + 1, and pt_len = body − 16n. This is unit-tested.

### 5.5 Random access (homelab, restore)

1. Range-read the prefix, unwrap the file key and verify the header MAC.
2. Derive pt_len from the object length (§5.4). Compare it with the catalog size.
3. **Authenticate the final chunk** (decrypt it with last = 1). Only then serve chunk *i*: one 65,552-byte range read, decrypted with counter *i*.

Without step 3, an object truncated exactly at a chunk boundary still serves intact middle chunks. The reviewers reproduced this, and the fix is tested. The `age` crate's `StreamReader::seek` does not do this check, so use it only on objects the ingest step has already verified.

## 6. Pass 1: dedup and integrity values

- stat before → one sequential read → stat after. A changed stat means exit "unstable" and retry once the file is quiescent (tested with a concurrent writer).
- sha256 = SHA-256(plaintext). It never leaves the device in plaintext; it travels only inside the metadata ciphertext.
- dedup_key = HKDF-SHA256(ikm = family_secret, salt = empty, info = `reliquary/v1/dedup-key`). dedup_id = HMAC-SHA256(dedup_key, plaintext).
  - The key derivation adds domain separation and versioning to the settled "HMAC(family secret, content)". The owner should confirm (§16, D-4).
- Cost: 2 hash computations per byte. The first prototype used 3, and 4 counting pass 2.

## 7. Multipart layout and part-size policy

- P = k·65,552, where k = 80·2^j is the smallest value that gives ≤ 10,000 parts. P must also be ≤ 5 GiB, so j ≤ 9.
- num_parts = ceil(ct_len / P). Part *p* covers bytes [p·P, min((p+1)·P, ct_len)). Wire part numbers start at 1.
- Part *p* ≥ 1 covers chunks p·k−1 … (p+1)·k−1. The boundary chunk belongs to both neighbours. Generating in order encrypts it once (a one-chunk cache); otherwise it is encrypted twice, with identical output. This holds for any prefix_len from 1 to 65,551 (unit-tested).
- **One part (ct_len ≤ P, i.e. files ≤ ~5.2 MB):** a single PUT with no resume state. An interrupted PUT is retried from scratch with fresh randomness (tested).

| k | P (bytes) | Max object (10,000 parts) | Buffered-mode memory |
|---|---|---|---|
| **80 (default)** | **5,244,160** | **52.4 GB** | 5.2 MB |
| 160 | 10,488,320 | 104.9 GB | 10.5 MB |
| 320 | 20,976,640 | 209.8 GB | 21 MB |
| 1,280 | 83,906,560 | 839 GB | 84 MB |
| 40,960 (max) | 2,685,009,920 | 26.85 TB | streaming only |

- Base 80, not 128, cuts the retransmission cost of a mid-part cut by 37% (reviewer E9).
- The extra UploadPart requests over 10 TB come to about $3 of R2 Class A operations in total (about 0.7 M extra requests at $4.50 per million).
- With streaming windows, memory does not depend on P.

## 8. Resumption

### 8.1 Persisted state (per in-flight upload)

| Item | Location (prototype) | Secret? | Written | Deleted |
|---|---|---|---|---|
| K_upload (32 B) | keystore entry `<id>.key`, mode 0600 | yes | at start | on complete or abort |
| Sealed state | `<id>.state`, 0600 | sealed | **once**, at start | on complete or abort |
| Journal | `<id>.journal`, 0600 | no (MAC'd) | appended | on complete or abort |
| Metadata record | `<id>.meta.age` | homelab ciphertext | at start, **before any content byte** | after the receipt |
| Pending record | `pending/<id>.json` | no, but sensitive (sha256, path) | at complete | after the receipt |
| Lock | `<id>.lock` (flock/LockFileEx) | no | each process | at complete |

Nothing else is stored. Ciphertext exists only in the buffer or window in flight (or in the iOS spool, §8.6).

**Sealed state:**

```
"RQUS\0\0\0\x02" ‖ u16be id_len ‖ upload_id ‖ nonce(12) ‖ AES-256-GCM(K_upload, nonce, JSON, aad = magic ‖ upload_id)
```

- JSON fields:
  - identity: v, upload_id, r2_upload_id, object_key, device_id;
  - source: source_path, snapshot {size, mtime_ns, ctime_ns, file_id};
  - layout {pt_len, chunks_per_part, prefix_len};
  - hashes: sha256, dedup_id;
  - keys: prefix_b64 (the 184 B prefix), **payload_key_b64 (the only secret)**;
  - metadata: meta_file, meta_sha256.
- AES-GCM is used because a non-exportable Android Keystore key can do it inside the keystore. On iOS, wrap with a Secure Enclave P-256 ECIES key.
- The payload key is persisted instead of the file key. It can regenerate or decrypt only this payload and cannot mint new header MACs.

**Journal:**

```
"RQJ\x01" then records: type u8 ‖ len u32be ‖ body ‖ HMAC-SHA256(journal_key, "RQJ1" ‖ seq u64be ‖ type ‖ len ‖ body)[0..16]
```

| Record | Body |
|---|---|
| TAGS (type 1) | first_chunk u64be ‖ n × 16-byte tags for consecutive chunks |
| DONE (type 2) | part_number u32be (1-based) ‖ ETag as returned by R2, stored verbatim |

- journal_key = HKDF(payload_key, `reliquary/v1/journal`).
- A torn **final** record (crash mid-append) is dropped. Any other bad record means abort and restart.

**Size and write cost:**

- About 1.4 KB per 5 MiB part (0.027%).
- Two fsynced appends per part, i.e. two 4 KiB page writes.
- Measured at 10,000 parts: 8.75 KB per part and 87.5 MB in total. The first prototype rewrote the whole state after each part and reached about 10.4 GB.

### 8.2 Algorithm

1. **start:**
   - pass 1;
   - Worker check: missing? Claim it; get the UploadId;
   - build the header;
   - build, sign and persist the metadata record;
   - create K_upload, seal the state, create the journal.
2. **For each part not marked DONE** (in any order):
   - split it into windows (whole part, or W chunks);
   - for each window, call `gen_range` (§8.3), re-stat, then release the window;
   - after the ETag arrives, append DONE.
3. **complete:**
   - CompleteMultipartUpload;
   - write the pending record and PUT the metadata record;
   - **delete K_upload**, the state and the journal.
4. **On receipt:** verify it (§10), mark the file protected, and delete the pending record and the local metadata copy.

**Abort and restart** (a fresh key and staging key, back to pass 1) happens when:

- the source stat changes (exit 65);
- a tag mismatches (65);
- the state or journal is corrupt, or the key entry is missing (76);
- R2 reports NoSuchUpload *and* the Worker says the upload is not completed;
- the 7-day auto-abort fires.

Two outcomes are not restarts:

- Source missing (66) keeps the state for later.
- Another process holding the lock (73) means back off.

### 8.3 The release rule (the invariant)

> No byte of chunk *c*'s ciphertext may reach the network, a shared temp file or the spool until either
> (a) its freshly computed tag equals the journaled T[c], or
> (b) T[c] has been durably appended to the journal.
> `gen_range` is the only encryption path and returns only windows that satisfy this rule.

- **Why tags work as change detectors:** for a fixed one-time Poly1305 key, two different 64 KiB ciphertexts collide with probability ≤ 8·⌈L/16⌉/2^106 = 2^-91. File edits are independent of the random key. The tag is computed anyway, so the check costs no extra hashing.
- **Why stat checks are still needed:** a chunk that was *never* transmitted re-encrypts cleanly. There is no reuse, but the object would no longer match the pass-1 hashes. The homelab catches this (test S4), but stat checks catch it on the device first (S5).

### 8.4 What the persisted key allows

It can encrypt or decrypt only this one in-flight object, whose plaintext is already on the device. After completion, the device holds nothing that can decrypt any backup. Deleting the per-upload key entry makes any leftover copies of the state useless (tested).

### 8.5 Staging keys, claims and R2 reconciliation (design rules)

- **Staging key:** `staging/<dedup_id>/<upload_id>`. There is one object per upload, never overwritten. The Worker never presigns an existing or committed key.
- **Duplicates:** the homelab keeps the first verified copy and drops the rest.
- **ListParts:** never adopt a listed part unless its ETag equals the one in the journal. Parts belong to exactly one UploadId and one K_upload.
- **NoSuchUpload:** ask the Worker for the claim or commit status before restarting. This covers a crash after Complete and before the state was deleted.

### 8.6 Forward-only sources (iOS PhotoKit)

- `gen_range` reads through a `ChunkSource`. Random-access sources:
  - desktop files;
  - Android files and most `content://` URIs;
  - iOS `AVURLAsset` file URLs.
- A forward-only source (`PHAssetResourceManager`) restarts and skips forward when it needs an earlier offset.
- **Rule:** per wake, open one stream and generate as many consecutive parts as the spool allows. Enqueue them all in one background-session wake.
- Measured on a 20-part file:

  | Parts per wake | Source reads (× file size) |
  |---|---|
  | all in one wake | 1.0× (each chunk encrypted once) |
  | 5 | 2.6× |
  | 1 | 11× |

- Total reads ≈ S·(w+1)/2 for w = ceil(S / spool) wakes. For example, a 4 GB video with a 512 MiB spool reads about 4.5× its size.
- Prefer the `AVURLAsset` URL, which gives random access with no copy.

## 9. Metadata record v1 (signed)

- The record is a separate standard age v1 file (§5, hedged with the SHA-256 of the record) for the homelab key. It is built and uploaded in one shot, with no resume.
- Plaintext:

```
<line1: compact JSON body>\n
{"alg":"ed25519","key_id":"<device_id>","sig":"<b64 Ed25519 over 'reliquary-meta-v1\n' ‖ line1>"}\n
<ASCII spaces to a multiple of 512 bytes>
```

- The body has these fields:

  | Group | Fields |
  |---|---|
  | Identity | `v:1`, `type:"reliquary.file-meta"`, `device_id` |
  | Content binding | `dedup_id`, `sha256`, `size` |
  | Object | `content_object: {key, header_mac}`, or **`null` for a dedup hit** |
  | Source | `source_locator`, `path`, `name` |
  | Snapshot | `mtime_ns`, `ctime_ns`, `file_id`, `recorded_at` |

  The snapshot fields are from pass 1, so the record describes exactly the version that was uploaded.
- The signature covers the exact bytes, so no JSON canonicalization is needed.
- The homelab rejects any of these:
  - an unknown key_id;
  - a bad signature;
  - `device_id` ≠ key_id;
  - trailing data other than spaces.
- **Binding:**
  - Always by (dedup_id, sha256, size), all verified against the decrypted content.
  - Also by `header_mac`, when the device uploaded the object itself.
- **Storage key:** `meta/<device_id>/<random>.age`. It does not contain the dedup_id.

## 10. Commit receipts and trust bundle

**Receipt**, relayed by the Worker:

```
{"committed_at":…,"dedup_id":…,"device_id":…,"meta_sha256":…,"size":…,"type":"reliquary.commit-receipt","v":1}\n
{"alg":"ed25519","key_id":"homelab-receipt-1","sig":"<b64 over 'reliquary-commit-v1\n' ‖ line1>"}\n
```

- The receipt contains no plaintext SHA-256. It carries the dedup_id, which binds the content under the family secret.
- **File protected:** the receipt verifies under the pinned receipt key and matches this device's pending record (dedup_id, size, device_id, meta_sha256).
- **Dedup "present" answer:** counts only if the Worker returns a valid receipt from any device for (dedup_id, size), checked in content-only mode. The device still uploads its own record and waits for its own receipt (tested).

**Trust bundle:**

```
{"v":1,"recipient":"age1…","receipt_key":"<b64 Ed25519>"}
```

- The pin is SHA-256(bundle bytes). It is carried in the invite QR code or on the USB kit, never learned from the Worker.
- The device refuses a bundle that does not match the pin. It also refuses a recipient that is not lowercase canonical Bech32 (uppercase and Bech32m are refused; tested).

## 11. Homelab ingest rules (implemented in `ingest`)

1. Decrypt the metadata with the age crate, then verify its signature and `device_id`.
2. Check that the object length is valid and equals the record's size.
3. Check that the header MAC matches `content_object.header_mac`.
4. Decrypt the whole object **to a temp file** while computing SHA-256 and HMAC.
5. Require size, sha256 and dedup_id to match. Otherwise delete the temp file and reject.
6. Atomically rename the plaintext into the store, update the dedup index, append the catalog entry, then sign the receipt.
   - A dedup-hit record whose content is not yet committed gets "pending" and no receipt.
   - USB bundles are the object split at part boundaries: part files of ≤ 2.5 GiB, so FAT32 works. Ingest concatenates them.
7. Mark the dedup ID committed in D1 only after step 6.

## 12. Threat analysis

### 12.1 Residual risks (after fixes)

| ID | Risk | Mitigation or status |
|---|---|---|
| R-1 | Keystream reuse if the release rule is bypassed (a new code path, or a journal rolled back by a device-backup restore) | The rule sits in the `gen_range` API. Wire-consistency checks on every test case; a mutation test that removed the tag check failed 2 tests. Exclude the state and journal from OS and cloud backups. Production code needs dedicated review of this invariant |
| R-2 | During an upload, the device holds the payload key of its in-flight object | It gains nothing new, because the plaintext is local. The key is per-upload and deleted on completion |
| R-3 | age has no sender authentication; anyone with the public key can create objects | Objects count only when bound to a device-signed record whose hashes the homelab verifies |
| R-4 | Exact plaintext sizes leak (ct = 184 + n + 16·chunks) | Accepted for v1 unless the owner wants padding (D-7) |
| R-5 | The dedup secret sits on 10–25 devices. One leak lets whoever holds the cloud data test all historical IDs, with no forward secrecy | Restate the ADR-0001 property (D-6). Rate-limit and log presence queries; answer only for IDs about to be uploaded |
| R-6 | Harvest-now-decrypt-later: objects are X25519-only | D-2 (ML-KEM hybrid stanza) |
| R-7 | Header shape changes (PQ or recovery stanza) | prefix_len is a layout field. The layout math is unit-tested for prefixes of 1–65,551 B. `open_prefix` (the range reader) handles only the one-stanza shape and must be generalised |
| R-8 | RNG failure (VM clone) | Hedged derivation (§5.2) |
| R-9 | A compromised Worker lies about "present" or suppresses uploads | Receipts: a device never shows "protected" without one. A pending claim must never cause another device to skip the file for good |

"Spike" = fixed and tested in the prototype. "Design" = a rule written here that needs no prototype. "Open" = see §15.

| # | Finding (severity) | Resolution | Status |

| C4 | The keystream invariant needed whole-part buffering; streaming broke it (major) | Chunk-level release rule with journaled tags; windowed `gen_range` (tests S2, S3, S4; wire consistency checked on all 83 round trips and the safety cases) | Spike |

## 14. Throughput

Setup: one thread, a 1 GiB file in the page cache, best of 3 runs, MB = 10⁶ B/s, Xeon 2.1 GHz VM with SHA-NI, AVX2 and AVX-512.

"Portable" forces the non-SIMD SHA-2, ChaCha20 and Poly1305 backends as a rough stand-in for ARM before the upgrade.

| Measure | Default | Portable | First prototype (default / portable) |
|---|---|---|---|
| SHA-256 alone | 1,136 | 299 | 1,100–1,180 / 251 |
| HMAC-SHA256 alone | 1,141 | 277 | 1,080–1,140 / – |
| ChaCha20-Poly1305 alone | 1,030 | 381 | 1,080–1,270 / 406 |
| Pass 1 (SHA-256 + HMAC, from file) | 668 | 140 | 452–482 / 96 |
| Pass 2 (encrypt + tag journal) | 922 | 355 | 537–599 / 150 |
| **End to end (pass 1 + pass 2)** | **≈ 387** | **≈ 100** | ≈ 260 / ≈ 58 |

- Both passes are needed, because the dedup ID has to exist before the Worker is asked.
- **ARM with the new dependencies:**
  - sha2 0.11 detects ARMv8 SHA-2 at runtime. iOS targets even enable it at compile time.
  - chacha20 0.10 selects NEON on aarch64 by default.
  - poly1305 0.9 has **no ARM SIMD backend**. It may become the bottleneck on phones; the alternatives are `ring` or `aws-lc-rs` for the AEAD.
- Not measured on phones; flash I/O and heat throttling are not modelled.

## 15. Open issues

1. **R2 behaviour (needs a real R2 spike):**
   - presigned UploadPart with retries, and byte-identical re-upload of a part;
   - the ETag format and checksum headers;
   - ListParts and ETag reconciliation;
   - conditional CompleteMultipartUpload (If-None-Match);
   - maximum presigned-URL lifetime against iOS queue delay;
   - whether the 7-day auto-abort is configurable. Warn "large file keeps expiring" and suggest USB.
2. **Phone benchmarks** on a low-end Android (A53/A55) and an iPhone, including battery. Also evaluate `ring` or `aws-lc-rs` against Poly1305 in portable mode.
3. **Worker claim protocol:**
   - TTL;
   - reset on rejection;
   - the receipt relay;
   - rate limits on presence queries.
4. **Enrollment details:**
   - family-secret delivery;
   - device signing-key registration through an admin-authenticated channel;
   - revocation;
   - signed rotation of the trust bundle.
5. **USB bundle manifest:**
   - format and device signature;
   - a check before writing that the volume's file-size limit fits the parts.
6. **A general age header parser** for range reads with more than one stanza (PQ or recovery).
7. **Production implementation:**
   - SQLite in place of state/journal files;
   - per-platform keystore wrapping;
   - backup exclusion (`NSURLIsExcludedFromBackupKey`, `dataExtractionRules`);
   - Windows `seek_read` and durability flags;
   - an in-memory tag map loaded per part rather than whole.
8. **C2SP age test-kit vectors** were not run against our encoder. Interop was checked by round trips only. Also test a newer age release than 1.1.1.
9. **Zeroization is best effort:** serde/base64 intermediates and in-flight buffers can leave copies in memory.
